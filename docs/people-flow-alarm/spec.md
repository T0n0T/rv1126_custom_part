# 端侧人流检测与 GB28181 告警上送规格

状态：已确认（2026-09-01；生产参数仍以 T1/T3/T9 验收为准）
目标平台：RV1126B 端侧设备、GB28181 上级平台、WVP 兼容接入  
本阶段交付：规格定义，不包含生产代码、实施计划和任务拆分

## Problem Statement（问题陈述）

当前设备已经具备采集、编码、点播和 GB28181 信令能力，但尚未形成可用于生产的人流事件链路：没有常驻的人体检测与跟踪分支，没有统一的事件生命周期和计数语义，没有可重放的事件通道，也没有构建并上送 GB28181 Alarm MESSAGE 的完整能力。

现有媒体事件通道只向当时已连接的客户端广播，客户端断开或发送失败后事件会丢失；上层媒体 RPC 以短连接请求为主，不适合持续订阅。当前快照能力也不可直接作为触发帧证据使用。因此，若只在检测回调中临时发送一次告警，无法保证断网重试、进程重启恢复、顺序、去重或图片与事件的准确关联。

WVP 当前对标准 Alarm 的处理是先解析告警元数据，再异步从媒体流抓取一张图片。这张图通常只是告警附近的帧，不是端侧算法实际触发的那一帧；标准 GB28181 Alarm XML 本身也不适合承载 JPEG/Base64 大图。系统需要同时支持 stock WVP 的标准兼容路径，以及需要 WVP 适配才能实现的精确证据路径。

## Solution（方案）

在端侧媒体主链的 NV12 DMA-BUF 数据上增加一个常驻、低分辨率、有限队列的分析分支。首版使用 RockIVA 视频模式完成人体检测与单路视频内跟踪，并把厂商回调转换为与算法实现无关的标准观察结果。独立事件引擎基于观察结果和规则生成 `START`、`UPDATE`、`END` 事件，维护当前人数、进出增量、去抖和恢复语义。

事件产生时，端侧按策略保存关联 JPEG 和证据元数据，并先写入有界持久事件日志。GB28181 守护进程通过长连接订阅、确认和断线重放消费事件，再把事件映射为标准 Alarm MESSAGE。系统提供两种图片策略：

- `stock_wvp_pull`：只发送标准 Alarm，由 WVP 在收到告警后从视频流抓取近邻帧；兼容现有 WVP，但不承诺同帧。
- `exact_evidence`：端侧保存算法触发帧并通过独立、可重试的 HTTP 证据适配器上传或供平台获取，以 `event_id` 和 `evidence_id` 关联；需要 WVP 侧配套适配。

首版不移植 `wvp-ssv` 的 ONNX Runtime/OpenVINO、主机解码和 BoT-SORT 栈。系统保留可替换的推理后端边界，使后续可以增加自维护的 RKNN 后端，但不同后端的统计结果不得默认合并。

## User Stories（用户故事）

1. 作为部署人员，我希望人体检测在设备上常驻运行，从而即使无人点播也能持续产生事件。
2. 作为部署人员，我希望分析分支的分辨率和帧率可配置，从而分析负载不会破坏主编码链路的稳定性。
3. 作为平台运维人员，我希望每个观察结果都标明通道和流纪元，从而流重启后复用的跟踪 ID 不会被误认为同一个人。
4. 作为分析数据使用者，我希望每个被跟踪目标在一个流纪元内拥有稳定的 RockIVA 对象 ID，从而可以连续关联轨迹和规则判断。
5. 作为分析数据使用者，我希望检测坐标同时声明来源帧尺寸，从而边界框和规则坐标可以无歧义地转换。
6. 作为平台运维人员，我希望 ROI 当前人数与越线流量分别上报，从而“当前有几人”不会与“进入/离开过几人”混淆。
7. 作为平台运维人员，我希望越线方向明确，从而进入和离开增量可以分别累计。
8. 作为平台运维人员，我希望系统不宣称全局唯一访客数，从而跟踪 ID 复用不会被包装成系统无法保证的业务指标。
9. 作为规则管理员，我希望每个通道可配置人体、ROI、入侵和越线规则，从而同一固件可以适配不同场景。
10. 作为平台运维人员，我希望事件拥有稳定的 `event_id`，从而 Alarm、重试和证据可以可靠关联。
11. 作为平台运维人员，我希望事件阶段表达为 `START`、`UPDATE` 和 `END`，从而适配后的消费者可以明确理解生命周期。
12. 作为平台运维人员，我希望候选检测经过可配置的确认过程，从而单帧误检不会立即形成告警。
13. 作为平台运维人员，我希望去抖、消失宽限和冷却时间可配置，从而规则边界附近的抖动不会触发告警风暴。
14. 作为平台运维人员，我希望 `UPDATE` 可以限频和关闭，从而频繁的人数变化不会压垮 SIP 信令。
15. 作为平台运维人员，我希望流重置或进程重启后活动事件带明确原因结束，从而陈旧事件不会永久保持开启。
16. 作为事件复核人员，我希望事件时间表示采集时间而不是发送时间，从而告警能与录像时间线对齐。
17. 作为事件复核人员，我希望源 PTS 和帧 ID 独立于墙上时间保留，从而精确帧关联不只依赖时钟准确度。
18. 作为事件复核人员，我希望触发 JPEG 与事件携带相同的 `event_id`、`evidence_id`、帧 ID 和源 PTS，从而证据来源可审计。
19. 作为 stock WVP 运维人员，我希望收到符合兼容规范的 Alarm MESSAGE，从而现有 WVP 无需定制解析器即可展示告警记录。
20. 作为 stock WVP 运维人员，我希望明确 WVP 告警后抓图的限制，从而近邻帧不会被误称为精确触发帧。
21. 作为已适配 WVP 的运维人员，我希望精确证据通过独立 HTTP 通道传递，从而平台可以展示算法真正触发的帧。
22. 作为已适配 WVP 的运维人员，我希望图片和告警可以按任意顺序到达，从而任一记录后到时仍可完成关联。
23. 作为安全管理员，我希望精确证据传输具备身份认证和完整性校验，从而图片不能被冒充或静默篡改。
24. 作为隐私管理员，我希望证据保留时间和存储上限可配置，从而图片不会被无限期保存。
25. 作为平台运维人员，我希望 Alarm 类型映射可配置，从而越线、入侵和流量统计符合目标平台的解释。
26. 作为平台运维人员，我希望 SIP `SN` 始终只是消息序号，从而它不会被误用作帧号或跟踪序号。
27. 作为可靠性工程师，我希望事件在投递前写入持久日志，从而守护进程或网络短暂中断不会静默丢失重要告警。
28. 作为可靠性工程师，我希望事件订阅具备长连接、确认和恢复游标，从而重连后只重放尚未确认的投递。
29. 作为可靠性工程师，我希望投递采用至少一次语义和稳定幂等键，从而重试不会在上游制造失控的重复记录。
30. 作为可靠性工程师，我希望队列压力优先合并或丢弃 `UPDATE`，并保护 `START` 和 `END`，从而事件生命周期边界尽量完整。
31. 作为可靠性工程师，我希望损坏、过期或被永久拒绝的记录可观测，从而投递失败不会被误认为成功。
32. 作为运维工程师，我希望看到推理、跟踪、事件、证据、队列、重试和 SIP 结果的健康指标，从而可以分别诊断链路各阶段。
33. 作为运维工程师，我希望分析故障对视频编码采用失效开放策略，从而 NPU 或事件链路故障不会停止主视频流。
34. 作为运维工程师，我希望配置经过校验且默认值明确，从而非法规则或存储限制可以在启动时可预测地失败。
35. 作为固件维护者，我希望推理后端隐藏在稳定的观察结果契约之后，从而未来 RKNN 模型可替换 RockIVA，而无需重写事件和告警层。
36. 作为固件维护者，我希望提供影子对照模式，从而未来后端可与 RockIVA 比较，但不会合并或重复统计结果。
37. 作为测试人员，我希望使用录制回调序列和确定性时钟驱动事件引擎，从而不依赖真实 NPU 也能测试生命周期和时序行为。
38. 作为发布负责人，我希望在真实板卡上验收精度、时延、资源、背压和长期稳定性，从而主机测试不会被误当成设备验证。

## Implementation Decisions（实施决策）

### 1. 责任与模块边界

实现按以下责任链分层：

| 边界 | 责任 |
| --- | --- |
| `AnalyticsBackend` | 接收分析帧并输出与具体后端无关的观察结果。 |
| `RockIvaBackend` | 管理 RockIVA 生命周期、帧提交/释放和回调归一化。 |
| `NormalizedObservation` | 承载检测、跟踪、时间戳和原始规则事实，不感知 GB28181。 |
| `EventEngine` | 管理规则判断、计数语义、确认、去抖和 `START/UPDATE/END`。 |
| `EvidenceCache` | 选择、编码、索引、保留和过期与事件关联的 JPEG 证据。 |
| `EventJournal` | 持久保存有序投递，并实现确认、重放和压力策略。 |
| 事件桥 | 通过本地长连接向通过认证的消费者传输日志记录。 |
| `DeliveryOutbox` | 在守护进程中持久接收事件，并分别记录 Alarm 与证据 sink 的投递状态。 |
| `AlarmSink` | 将事件映射为 GB28181 Alarm XML，并经已注册的 SIP 会话投递。 |
| `EvidenceSink` | 启用精确证据模式时，以独立于 SIP 的方式投递证据。 |

首版人体检测和单路视频内跟踪以 RockIVA 输出为权威。RockIVA 不负责业务事件生命周期、累计流量、证据保留或 GB28181 格式化。RockIVA BA 结果可作为原始规则事实输入，但最终去重和生命周期决策仍由 `EventEngine` 负责。

`media_engine` 负责常驻分析分支、`RockIvaBackend`、事件引擎、证据缓存、生产者日志和本地订阅服务。`gb28181_daemon` 负责订阅客户端、持久投递 outbox、Alarm 构建/SIP sink 和精确证据 HTTP sink。可选的 WVP 适配器负责在服务器侧按事件/证据 ID 幂等关联图片。

未来的 `RknnBackend` 必须实现同一观察结果边界。本规格只保留该扩展接缝；模型转换、预处理、后处理和跟踪器实现均延后。

### 2. 常驻分析分支

- 分析分支随基础媒体管线创建，其运行不依赖 GB28181 INVITE 或点播状态。
- 分支从现有支持 DMA-BUF 的原始视频 tee 获取 NV12 帧，并使用可配置的缩放尺寸和采样率。
- 分支采用有界的最新帧策略。推理慢于采集时丢弃陈旧分析帧，不阻塞采集或编码。
- Buffer 和 DMA-BUF 的生命周期保持到 RockIVA 释放回调确认完成；关闭时先排空或取消未完成帧，再销毁资源。
- 分析故障与主视频路径隔离。只要基础管线仍健康，设备报告分析降级但继续提供视频服务。

### 3. RockIVA 行为

- RockIVA 采用 `ROCKIVA_MODE_VIDEO` 视频模式，从而获得对象跟踪状态和 `objId`。
- 配置必须通过 DET 回调或 `detectResultMode=1` 等价的全量结果模式取得完整检测结果；只返回规则触发对象的模式不足以进行占用人数统计。
- 首版人流逻辑只处理 person 类别。
- 跟踪身份的作用域为 `(channel_id, stream_epoch, obj_id)`；不承诺跨纪元、跨进程重启或跨摄像机唯一。
- RockIVA 跟踪状态需要归一化，厂商特有状态值不得泄漏到事件或 GB28181 契约。
- RockIVA 阈值、模型选择和 BA 能力属于部署配置，并必须记录在诊断信息中。

### 4. 归一化观察结果契约

每个观察结果均带版本，且至少包含：

- 通道标识 `channel_id` 和 `stream_epoch`；
- 纪元内单调递增的 `frame_id`；
- 带明确单位/时基的 GStreamer `source_pts`；
- 采集墙上时间估计值 `capture_time` 和 `clock_state`；
- 分析帧宽度和高度；
- 后端名称以及后端配置/模型版本；
- 零个或多个人体观察结果，分别包含 `track_id`、`bbox`、`class`、`score` 和归一化 `state`；
- 可选的原始规则事实，包括 `rule_id`、`rule_type`、`direction`、后端置信度和
  可选的责任 `track_id`；`track_id` 缺失表示规则级事实，而不是伪造目标身份。

缺失值必须明确保持缺失，不得根据 SIP `SN`、接收顺序或墙上时间伪造。重复帧和乱序帧在该边界识别，且不得使事件引擎状态倒退。

帧与时间关联约束：RockIVA 结果对象的 `frameId` 可能为零或未提供时，必须使用
`RockIvaDetectResult.frameId` 作为检测回调的输入帧关联键；不得把对象
`timestamp`、GB28181 `SN` 或稀疏 Alarm 字段伪造成 `source_pts`、帧序或采集时间。
`source_pts` 只有在来源时基可信且单位明确时才填写，否则保持缺失并标记
`clock_state`；`capture_time` 必须来自采集时钟而非告警到达时间。检测框如超出声明
的坐标范围，由适配器按契约裁剪并记录，或原样保留但不得静默改变。

### 5. 计数与事件语义

- `person_count` 表示引用观察时刻，配置 ROI 内当前已确认的人体轨迹数。
- `delta_in` 和 `delta_out` 表示由已确认轨迹或归一化 BA 事实产生的方向性越线增量。
- 如果暴露累计值，其作用域必须是通道和明确声明的计数纪元，且不得称为唯一人数。
- 每个事件包含模式版本、`event_id`、`channel_id`、`stream_epoch`、`event_type`、`rule_id`、`phase`、`event_seq`、`reason`、`event_time`、`source_pts`、`frame_id`、`person_count`、`delta_in`、`delta_out`、可选的责任 `track_id` 列表和可选 `evidence_id`。
- `START` 在确认后只产生一次。`UPDATE` 只针对配置为有意义的变化产生并受限频控制，默认不投递到 GB28181。`END` 在配置的恢复/宽限条件满足后产生，是否投递到 GB28181 由平台配置决定。
- 正常流重置时，在纪元推进前以重置原因为活动事件收尾。异常进程重启后，在接受新纪元事件前，以重启原因为恢复到的活动状态收尾。
- 生命周期键在本地重试期间保持稳定，重传不得生成新的 `event_id`。

### 6. 时间模型

- 源 PTS 是规范帧时间线，直接来自 GStreamer buffer。
- `AlarmTime` 从采集时刻的墙上时间映射得出，而不是守护进程收到或发送事件的时间。
- 每个流纪元建立独立的 PTS 到墙上时间映射，并以受控方式刷新，避免 NTP 校时导致帧顺序倒退。
- 时钟未同步状态和估计时间误差必须可观测。系统仍可发送告警，但映射无效时不得把墙上时间标记为帧级精确。
- SIP `SN`、日志投递序号、事件序号、帧 ID 和源 PTS 是不同概念，禁止相互代替。

### 7. 事件状态机

- 原始规则命中首先进入候选状态，并在达到可配置的确认次数或持续时间后激活。
- 激活后，短暂检测缺口由消失宽限期吸收。
- 边界抖动由迟滞/去抖控制，已结束事件的重复触发由冷却时间控制。
- 轨迹消失、规则重配置、流重置、分析关闭和进程重启分别产生明确的结束原因。
- 多个人可以共同构成一个占用事件；越线事件则记录负责的作用域内轨迹和方向。具体分组策略按规则定义并带配置版本。
- 规则配置变化时推进规则/配置版本。现有事件要么按旧版本结束，要么明确以重新配置原因为结束；不得原地改变其语义。

### 8. 证据模型与投递

证据记录至少包含 `evidence_id`、`event_id`、通道、流纪元、帧 ID、源 PTS、采集时间、JPEG 本地对象键/路径、尺寸、字节数、校验值、本地存储状态、投递状态和过期时间。本地路径只用于端侧内部索引，不进入标准 Alarm XML。

- 证据优先选择精确触发帧。若该 buffer 已不可用，只有在记录时间/帧差并将证据明确标为近似时，才可选择缓存中的最近帧。
- JPEG 创建和文件发布必须原子化，事件不得引用尚未写完的图片。
- 缓存容量有限。已确认或过期证据按保留策略删除；正在重试的证据保护到其重试/保留上限。
- 启用精确证据时，生产者在消费者确认已持久取得图片内容或有效保留租约前不得删除 JPEG。实现计划可在“复制/硬链接到 outbox”和“共享内容寻址缓存加持久租约”之间选择，但不能只传递一个可能失效的临时路径。
- `stock_wvp_pull` 不在 Alarm XML 中发送图片字节或端侧本地路径。WVP 异步抓取附近帧，结果明确归类为近似平台证据。
- `exact_evidence` 通过独立且经认证的 HTTP 适配器发送 JPEG。默认部署方向为设备向平台上传；网络拓扑需要时可选择平台向设备获取的适配器。
- Alarm 和证据具有独立的持久投递状态与重试计划，并通过 `event_id` 和 `evidence_id` 关联；两种传输都不假设到达顺序。证据失败不得阻塞 Alarm sink 投递。
- 标准 GB28181 Alarm XML 中禁止嵌入图片二进制或 Base64。

### 9. 持久本地事件桥

- 生产者必须先把归一化事件追加到有界持久日志，再向消费者报告事件可用。
- 日志记录获得单调递增的投递游标，该游标独立于事件序号和 SIP `SN`。
- GB28181 守护进程采用长连接订阅，不复用现有短连接请求/响应 RPC 模式；重连或重启后从最后确认游标继续。
- 守护进程先按幂等键把记录写入自己的持久 `DeliveryOutbox`；精确证据模式下还必须持久取得图片内容或保留租约，然后才能确认生产者日志游标。守护进程在持久接收前崩溃时由生产者重放；持久接收后崩溃时由 outbox 恢复 sink 投递。
- outbox 分别维护 Alarm 与证据 sink 状态。成功的 sink 不因另一 sink 重试而重复发送；所有必需 sink 成功，或某个 sink 按明确策略进入终止失败/死信状态后，记录才可清理。
- 本地桥和平台投递都采用至少一次语义。幂等键由设备/通道标识、`event_id`、阶段和事件内序号构成；在响应丢失等不确定结果下仍可能产生上游重复，适配后的消费者必须按该键幂等处理。
- 退避采用带抖动的有界指数策略。永久校验/拒绝错误不能无限自旋，并必须可观测。
- 生产者日志或守护进程 outbox 出现压力时，先合并冗余 `UPDATE`，必要时再丢弃并计数。为 `START` 和 `END` 预留容量；存储耗尽必须表现为健康降级，不能静默隐藏。
- 日志损坏、不兼容模式版本和游标缺口必须有明确恢复行为和诊断信息。

### 10. GB28181 Alarm 映射

Alarm XML 必须符合目标 WVP 所兼容的 GB28181 配置，并包含 WVP 预期的标准字段：命令类型、消息序号、通道/设备 ID、优先级、方法、事件采集时间、描述和适用的告警类型信息。

- `CmdType` 为 `Alarm`。
- `DeviceID` 按当前目录身份模型标识产生告警的视频通道。
- `AlarmMethod` 默认采用视频报警值 `5`。
- `AlarmType` 默认映射为越线 `5`、入侵 `6`、人流/流量统计 `9`；所有映射均可按目标平台配置。
- `AlarmPriority` 由配置决定，并按 GB28181 支持范围校验。
- `AlarmTime` 使用事件采集墙上时间，并遵循平台兼容的格式和时区策略。
- `SN` 作为 SIP MESSAGE 序号独立分配，并独立处理回绕。
- `AlarmDescription` 可携带经过转义的紧凑关联元数据，例如模式版本、事件 ID、阶段、规则 ID、计数和证据 ID；标准接收成功不得依赖平台理解这些扩展语义。
- 默认发送 `START`。`UPDATE` 默认关闭，启用时必须限频。stock WVP 默认不发送 `END`，除非目标平台明确理解生命周期元数据，因为 stock WVP 会把每条 Alarm 当作独立告警记录。
- SIP 响应、超时和注册状态共同进入重试决策。本地 socket 写入成功不等于平台投递成功。

### 11. WVP 兼容模式

- 在 `stock_wvp_pull` 模式中，成功指 WVP 接受并保存标准 Alarm，且可能自行从媒体流生成附近帧快照；系统不宣称触发帧精确性。
- 在 `exact_evidence` 模式中，WVP 需要一个小型服务端适配器，以幂等方式接收或获取证据，并按事件/证据 ID 关联告警记录。
- 厂商扩展不得替代标准 Alarm 字段。部署可按明确策略从精确证据降级为仅告警或 stock 拉图，并暴露降级后的证据状态。
- 后续若加入服务端媒体分析进行对照，其默认属于影子数据，不与端侧权威计数或事件生命周期合并。

### 12. 配置与可观测性

配置覆盖通道启用状态、分析分辨率/帧率、RockIVA 阈值、规则几何、确认/去抖/宽限/冷却参数、事件更新策略、Alarm 映射、证据模式/质量/保留、日志容量/重试限制、HTTP 认证和时钟健康策略。

诊断信息至少暴露分析输入/输出/丢帧速率、推理时延、活动轨迹、活动事件、证据成功/失败/字节数、日志深度/年龄/合并/丢弃、订阅连接/游标、SIP 尝试/结果/重试、时钟有效性、当前流纪元和配置/模型版本。日志携带关联 ID，但不输出图片内容或凭据。

### 13. 主要实现与测试接缝

最高价值的功能测试接缝，是从一组 `NormalizedObservation` 和帧开始，到外部可观察的事件日志记录、Alarm 信封和证据记录结束的完整路径。RockIVA 回调适配器以及真实 SIP/HTTP 传输保持为该接缝外围的薄契约边界。

这样既能在没有 NPU 和网络的环境中测试事件语义，也保留独立的真板与 WVP 互操作验证。实现不得把规则逻辑直接耦合到 RockIVA 回调结构或 GB28181 XML 字段。

## Testing Decisions（测试决策）

- 测试只断言外部可观察的契约、生命周期记录、XML、证据元数据和投递行为，不断言私有辅助函数调用、线程布局或容器选择。
- 确定性的单元/功能夹具向主要接缝输入带时间戳的归一化观察结果，并断言 `START/UPDATE/END`、计数、原因、证据选择和投递记录。
- RockIVA 适配器契约测试使用录制或合成的回调载荷，验证人体过滤、坐标转换、全量结果处理、对象状态归一化、纪元作用域和释放所有权。
- 事件引擎用例覆盖确认、单帧误检、多人、ROI 进入/离开、双向越线、边界抖动、短暂遮挡、纪元变化后的 ID 复用、重复/乱序帧、重配置、流重置和重启恢复。
- 计数测试分别验证瞬时 ROI 人数、方向增量和计数纪元；任何测试都不得把跟踪 ID 当成全局唯一访客。
- 时间测试使用假时钟和 PTS 序列，验证采集时刻 `AlarmTime`、NTP 跳变处理、无效时钟状态，以及 PTS、帧 ID、事件序号、日志游标和 SIP `SN` 的严格分离。
- 证据测试验证精确触发帧选择、带标记的最近帧降级、JPEG 原子性、校验值、保留、过期、存储压力以及告警/图片独立到达顺序。
- 日志/outbox 测试覆盖生产者崩溃、durable ingest 前后守护进程崩溃、断开/重启、未确认重放、重复确认、成功 sink 不因另一 sink 失败而重发、损坏游标、模式不匹配、重试耗尽，以及队满时保护生命周期边界的合并策略。
- Alarm 构建器使用黄金 XML 和解析器级断言，验证转义、WVP 必需字段、类型映射、时区、Unicode 描述、序号回绕以及不存在嵌入图片字节。
- WVP 兼容测试验证 stock WVP 能接受并列出标准 Alarm，且其生成的图片（如有）只视为附近帧快照。精确证据测试还需验证 WVP 适配器的幂等关联。
- 故障注入测试验证 RockIVA 失败、证据编码失败、存储满、本地 socket 中断、SIP 超时/拒绝和 HTTP 失败均不会停止主媒体流。
- 主机测试可以验证确定性逻辑和传输契约，但不能替代硬件验收。
- 真板验收测量目标场景检测准确率/召回率、跟踪 ID 切换、方向计数误差、触发到 Alarm 时延、触发到证据对齐、NPU/CPU/RGA 负载、内存增长、温度、分析丢帧、编码连续性、队列背压和重启恢复。
- 至少执行 24 小时目标板稳定性运行，覆盖正常流量和计划内上游中断；必须证明内存/存储有界且恢复后可成功重放。
- 在实现被判定完成前，必须基于代表性的标注数据集和部署配置确定场景准确率、计数误差、最大时延和资源预算阈值。
- 测试复用现有本地媒体 RPC 测试风格、RockIVA 回调/样例契约和 WVP Alarm 解析行为；新增测试围绕更高层的事件到 Alarm 接缝组织，不重复绑定每个内部模块。

## Out of Scope（范围外）

- 训练、量化、转换或调优自定义 RKNN 人体检测模型。
- 首版实现 `RknnBackend`。
- 把 `wvp-ssv` 的 ONNX Runtime/OpenVINO 推理、主机解码、Redis 发布或完整跟踪管线移植到端侧。
- 在真板证据尚未证明 RockIVA ID 无法达到约定计数阈值前，引入 BoT-SORT。
- 跨摄像机跟踪、ReID、人脸识别或全局唯一访客计数。
- 把 RockIVA 与另一后端的检测或计数合并成一个权威结果。
- 在标准 GB28181 Alarm MESSAGE 中嵌入 JPEG/Base64 图片数据。
- 把 stock WVP 的异步快照视为保证精确的触发证据。
- 全面重做 WVP 告警 UI、媒体服务器或数据库；`exact_evidence` 只要求另行限定范围的关联适配器。
- PTZ、语音对讲、完整事件录像、长期视频归档或回放时间线重构。
- 网络恰好一次投递；本契约采用至少一次投递加幂等消费。
- 在不可恢复的存储、硬件或 NPU 故障后保证分析继续运行；此类情况必须表现为健康降级。

## Further Notes（补充说明）

### 术语

- **观察结果（Observation）**：对某一个源帧中检测/跟踪对象的后端无关描述。
- **轨迹（Track）**：作用域限定在通道和流纪元内的后端身份。
- **占用人数（Occupancy）**：当前位于 ROI 内的已确认人数。
- **流量（Flow）**：在声明的计数纪元内，穿越配置线的已确认方向性次数。
- **事件（Event）**：由 `START`、可选 `UPDATE` 和 `END` 构成的业务/规则生命周期。
- **告警（Alarm）**：事件某一阶段的 GB28181 MESSAGE 表达；stock WVP 可能独立保存每条消息。
- **证据（Evidence）**：与事件关联的 JPEG 及来源元数据，可以是精确帧或明确标记的近似帧。

### 实施计划仍需确定的输入

本规格固定上述架构和契约。实施计划必须为分析分辨率/帧率、确认和冷却参数、规则几何来源、证据 JPEG 质量/保留、日志大小/年龄、WVP 精确证据端点/认证、告警优先级、时钟策略和板端验收阈值选择具体部署默认值。

这些值应根据目标镜头/场景、预期人群密度、可用存储、网络中断窗口和真实 RV1126B 基准得出。在上述边界内调整参数不需要重新设计事件契约；改变计数语义、证据保证或投递责任则需要重新审查规格。
