# flow_demo 需求规格

## 状态

本文记录首版需求及后续确认的增量。训练、RKNN 转换和真板运行时 smoke 已验证；截至 2026-11-13，11 段真实柜口视频已经完成 PC 解码后板端检测、跟踪和区域事件回放，但确认事件验收未通过，动作真值评测和板端本机文件解码仍待完成。板载摄像头已接通检测、事件核心和独立 DMA 预览，短测预览约 29.25 FPS、检测约 7.51 FPS；实时区域仍使用 DEBUG 示例，实际机位标定和真实取放验收待完成。

## 目标

构建独立的 RV1126B 售卖柜物体出入检测 Demo，以单类别安全帽 `helmet` 为例。系统以柜口过程视频识别逐次取出与放入动作，按临时轨迹计数，保留不确定情况的说明，并可在 RV1126B 上独立运行。

电脑端负责采集管理、标注、模型训练、模型转换、PC 回放与评测；板端负责视频解码、检测、跟踪、穿越判定和事件记录。最终验收必须包含板端实跑。

## 输入与运行模式

- 首阶段输入为预录视频；通过 sidecar 为每段视频指定会话 `open_pts_ms` 和 `close_pts_ms`。
- 会话时间使用视频源 PTS 表示，不使用处理完成的墙钟时间。
- 前后静态图片可用于辅助数量核对；图片本身不作为逐次取放动作的证据。
- 后续可使用固定机位实时摄像头。首版允许专门布置柜体、机位和补光，并要求物体穿越柜口时有足够连续可见画面。
- 文件回放采用阻塞回压并尽量处理每帧；实时模式使用有界队列，可丢弃旧帧。所有观测保留原始 PTS 和帧序号。

## 模型与流水线

- 检测类别只有 `helmet`，检测安全帽本体；不做人头／佩戴状态识别，不区分颜色、款式或单顶安全帽的永久身份。
- 训练基线为从通用预训练权重微调 YOLOv8n，单类别，输入 640×640。通用 PPE 测试集和 RKNN 真板 smoke 已完成；柜口视频上的检测精度、动作精度和端到端性能仍未验证。
- 电脑端负责训练、ONNX 导出和 RKNN INT8 量化；板端部署 RKNN 模型及匹配的运行时依赖。
- 目标媒体链路为 GStreamer 解码与调度、SSV `ssv-infer` 推理结构（新增 RKNN 后端并允许修改上层抽象）、SSV `ssv-track`／BoT-SORT 跟踪、本项目穿越与事件元素。
- 推理抽象须能表达 `float32`、`int8`、`uint8` 等张量及量化参数。RKNN 输出不应被迫在 backend 内无条件复制为 float；parser 在需要时按张量类型和量化参数读取。
- SSV 必要源码复制到本项目独立维护。复制时记录源 commit、裁剪文件、许可证及本地差异；不依赖 SSV 工作树路径。
- 不预先承诺 RKNN Toolkit、模型导出算子、NPU 输入格式、硬件预处理或零拷贝路线；这些需以当前 RV1126B SDK 和板端实测为准。

## RKNN 板端 smoke 门禁

2026-11-11 新候选模型按用户指定改为 `comp-2-freeze10.onnx`。其元数据为 YOLO26l、640×640、RGB/255，类别为 `helmet=0`、`head=1`，原始输出为 `[1,300,6]` 的端到端检测结果。候选验证须保留两类输出并重新查询量化属性；原 YOLOv8n 单类 DFL 六头解析器不适用于此模型。完整图实测虽可转换、加载和推理，但最终坐标/分数/类别共用 INT8 量化尺度导致分数与类别为零；因此部署输出须拆为 `/model.23/Sigmoid_output_0`（概率 `[1,2,8400]`）与 `/model.23/Mul_2_output_0`（已解码 xyxy `[1,4,8400]`），各自反量化后在 CPU 复现原图的两阶段 TopK(300)，不额外做 NMS。须记录裁剪节点并与原图数值对照。该候选的检测质量尚待评测，不改变动作事件的单类别 `helmet` 需求。

模型转换完成后，先用独立的 `board/rknn_smoke` 工具在 RV1126B 上验证运行时契约，再接入视频流水线。该门禁至少记录 RKNN API/驱动版本、模型输入输出属性、量化参数、重复推理耗时和输出样本；它不替代检测精度、跟踪、穿越或事件验收。

板端跟踪核心可单独接收按源帧号和 PTS 排序的检测 JSONL，运行 BoT-SORT、区域判定并写出轨迹、事件和会话摘要。当前已打通 PC 视频解码/预处理 → RV1126B RKNN 推理与坐标还原 → 检测 JSONL 的 3 帧同图、30 帧连续 smoke、168 帧全片分批检测和 11 段真实视频回放，并单独在板端验证了合成 JSONL 到动作事件的核心；11 段视频的区域 profile 已人工确认，但真实动作没有产生确认事件，动作真值评测及板端本机解码仍待验证。

RGB 联调入口按默认 30 帧分批传输、推理和拉回结果，保留全片源帧号与 PTS，合并后核对总帧数。默认 ADB 目标为用户指定的 192.168.1.63:5555，允许显式选择 ADB server 端口。运行前须通过有时限的 shell 查询核实 RV1126B 板型；枚举为 device 不能替代该检查。预检失败时保留日志并在视频预处理之前退出；每次 ADB 调用均设可配置超时，不自动重启设备或覆盖失败 run。

首轮以单输出 FP16 模型作为加载和输入路径基线。INT8 模型的输入和检测头输出均可能是量化张量，只有在板端查询到与转换元数据一致的 `type`、`qnt_type`、`zp`、`scale` 和形状后，才进入后处理适配。板端 smoke 使用固定尺寸 RGB 原始输入，预处理契约为 640×640、NHWC、RGB、padding 值 114；输入图像的 letterbox 参数必须同时保存，后续映射回原图坐标时使用同一组参数。

INT8 六头后处理按板端查询到的输出属性逐头读取原生 int8 NCHW 张量，以 `(q - zp) * scale` 反量化。三个 stride（8、16、32）的 box head 按每边 16 个 DFL bin 做 softmax 期望解码，score head 保持转换图中的 sigmoid 概率；之后以 `conf_min=0.001`、IoU `0.7` 做单类别 NMS，最多保留 300 个框。输出框先保持 640×640 模型输入坐标，并可用同一输入的 letterbox sidecar 映射回原图。PC 参考实现和板端实现须使用相同的量化参数、阈值和坐标约定。

## 逐次动作语义

每个机位的视频按自身原始画面坐标配置 `inside`、`transition`、`outside` 三个区域；柜内深处左右两角的画面可以提供不同的 zones JSON。区域使用归一化坐标，启动时校验边界和顺序；检测预处理的缩放、letterbox 或旋转必须映射回原始坐标后再判定。当前各机位分别处理，不跨机位融合轨迹。

运行部署使用每个机位独立的区域 profile，不把坐标写入代码或模型。安装时由人工从本机摄像头代表性视频帧点击描出三区多边形，并逐帧检查采样画面的可见性；标定工具同时记录视频 SHA-256、分辨率、标定帧号和源 PTS。只有操作员在检查完整区域覆盖后显式确认，profile 才能设为 `geometry_confirmed=true`。profile 在每次事件运行时与实际视频路径和 session ID 合成运行配置；换相机、镜头、裁剪或柜体位置后必须重新标定。真实业务视频仍须满足柜口穿越期间可见，否则不得生成确定事件。

- 轨迹满足 `inside → transition → outside`，确认取出 `take_out`。
- 轨迹满足 `outside → transition → inside`，确认放入 `put_in`。
- 每次完整有效穿越产生一次逐支动作；同一 `track_id` 后续反向完整穿越可再次产生事件。
- 过渡区内折返、轨迹丢失、目标合并或无法满足可见性约束时，不猜数量，记录 `uncertain` 原因。
- 同方向且时间相邻的逐支穿越按初始 1 秒可配置窗口合并成一次事件，保留涉及的 `track_ids`；该窗口需通过数据评测调整。
- 观测间隔按源 PTS 计算。超过待配置上限时，不可跨越缺失区间确认动作，应重新建立区域状态或标记不确定。
- 会话关闭时仍未完成的穿越记为不确定；会话存在任何未解决的不确定过程时，`result_complete=false`。已确认动作仍保留，但不把部分净变化表达成确定总数。

## 输出契约

除简洁日志及 `events.jsonl`，新增独立板载摄像头检测预览；不实现完整业务 UI 或 WVP 接入。事件记录至少包含：

```json
{
  "event_id": "session-001-event-003",
  "session_id": "session-001",
  "direction": "take_out",
  "count": 2,
  "track_ids": [12, 15],
  "status": "confirmed",
  "start_pts_ms": 4200,
  "end_pts_ms": 5900,
  "start_frame": 126,
  "end_frame": 177,
  "reason": "",
  "evidence": {
    "video": "take_out_001.mp4",
    "start_pts_ms": 4200,
    "end_pts_ms": 5900
  }
}
```

`direction` 为 `take_out`／`put_in`；`status` 为 `confirmed`／`uncertain`／`rejected`。首版只引用原视频与 PTS／帧号，不在实时流水线裁剪片段。会话摘要单独报告确认取出、确认放入、不确定过程和 `result_complete`。

## 板载摄像头与屏幕预览

2026-11-13 已有 RKNN 模型替换对照：保留当前 YOLO26 双输出 INT8 后处理，并在同一摄像头/事件/预览入口增加单类别 YOLOv8 六头 INT8 适配。运行时按查询到的输入和输出契约选择后处理；六头须校验 box_logits/helmet_scores 的节点名、NCHW 尺寸、INT8 类型、字节数、逐张量零点与尺度，DFL=16、NMS IoU=0.7，输出同一旋转摄像头坐标系的归一化 helmet 框。不得复用写死的历史量化参数，也不得把 FP16、完整图混合 INT8 或未知结构当成六头模型。首选 `helmet-yolov8n-heads-int8-eval`，切换由 `MODEL` 配置完成，默认 YOLO26 模型保留。先进行相同输入的数值回归，再做板端摄像头帧率/事件输出一致性检查；性能对比与真实取放准确率分别报告。

2026-11-13 色差与倒置修正：对照 `media_engine/src/aiq/aiq_ctrl.c` 的实际初始化和板端配置，以同一 AIQ 会话的 RGB/NV12 帧定位颜色契约，并回读 RGA 显示截图检查结果。AIQ 采用 normal/day 场景、normal 工作模式、自动对焦及同一 IQ 目录。用户反馈摄像头画面上下左右均颠倒，保留整屏横向布局，将独立相机旋转从 0 改为 180，并同步未确认的示例 profile；不改写正式标定或生产 media_engine。

同会话实测已定位 RGB24 口字节实际为 BGR：与相差 1.7 ms 的 NV12 full-range BT.601 参考相比，原顺序 MAE 4.206，交换红蓝后 0.326。保留已验证的 RGB24 DMA 采集口，增加明确的 `CAMERA_COLOR_ORDER=BGR` 板型适配；预处理及干净截图按 BGR 解读后输出真正 RGB，RGA 源格式使用 BGR_888。不通过白平衡或全帧复制补偿通道错误。标准 RGB 字节序设备可配置 RGB，文件回放输入仍为 RGB。

前一轮 2026-11-13 方向调整曾将 `CAMERA_ROTATION` 从 90 改为 0，并新增 `SCREEN_ROTATION=270`（角度统一为顺时针）；本轮将相机校正为 180，保留整屏 270，整个界面含文字/三区/框仍逆时针转 90°。原生面板仍为 480×800，逻辑界面为 800×480。RGA 合成相机与屏幕旋转，图层直接映射写入同一 DMA 输出，避免新增整帧 CPU 旋转。事件及标定仍使用独立摄像头坐标系 640×360；示例 profile 同步更新，已有正式 profile 不改写。

板端 `/tmp` 当前仅余约 3 MB，新实时 run 的输出改存 `/userdata/flow_demo/board-camera/`，本机 run 保存 `remote-run.txt` 以管理其位置；旧 `/tmp` run 仍支持查询和收集，历史产物保留。

2026-11-13 按用户要求直接接板载摄像头，独立入口位于 `board/`。采集、AIQ、RKNN、绘框和 KMS 显示均由 `flow_demo` 管理，不修改生产 `media_engine`。启动前由操作员停止占用摄像头/DRM 的服务；使用正常退出释放设备，不能以 SIGSTOP 代替资源释放。不修改开机启动，恢复原服务采用单独命令。

- 采集默认 `/dev/video25`、640×360 RGB24（实际字节 BGR）、30 fps，利用 ISP 缩放；摄像头编号、IQ 目录、采集尺寸、色序、旋转、置信度、屏幕尺寸、connector 和 plane 可通过参数调整。相机旋转默认 180°，整屏旋转默认 270°（逆时针 90°），面板仍为原生 480×800。
- 旋转后的图像是实时检测坐标系；RGB 640×640 letterbox 填充值 114，输出框还原为该坐标系的归一化 xyxy。显示保持比例并留黑边，预览使用当前帧，叠加最近完成的检测并明确标注源 PTS 差，不能将异步叠加描述为同帧结果。
- 实时 appsink 只保留最新一帧，保留源 PTS 和采集序号；记录采集、处理、跳过帧及推理/后处理/显示耗时。文件回放入口仍使用阻塞策略，不能共用实时丢帧设置。
- 屏幕显示 `helmet` 与 `head` 两类框、跟踪 ID、三区/状态及取放数，输出兼容现有跟踪输入的检测 JSONL。没有实时机位 profile 时只允许标记为 DEBUG 的示例区域调试，不显示正式取放结论，不将既有手机视频 profile 直接套用到板载摄像头。
- SIGINT/SIGTERM 正常停止采集、AIQ 和 KMS，释放 RKNN 与所有帧。保存独立 run 的日志、统计和可选画面快照。编译、实际采集、KMS 提交及用户肉眼确认分别报告。

2026-11-13 实时调试增量：用户反馈预览卡顿，并要求先接入取放事件和屏幕调试。预览从推理循环解耦，目标跟随 30 fps 采集；使用 V4L2 DMA-BUF → RGA 旋转/缩放 → DMA-BUF → KMS，避免预览整帧的 CPU 复制。CPU 只写输出 buffer 上的调试图层；检测分支暂保留已验证的 RGB 输入契约，不将局部 DMA 优化称为端到端零拷贝。分别统计预览 FPS、检测 FPS、DMA 输入/输出帧数和预览渲染数。

- 快速预览使用当前摄像头帧；框、ID、区域状态和事件来自最新完成的检测。屏幕明确显示 AI 结果与当前画面的源 PTS 差，过时超过 400 ms 的框隐藏。事件只使用检测源帧与 PTS，不能用预览刷新的帧补造观测。
- 接入既有 BoT-SORT 与 CrossingEngine，显示 inside/transition/outside 边界、轨迹 ID、当前区域/待穿越状态、累计取出/放入/不确定数及最近事件原因；实时落盘 tracks/events/summary，合并事件的增量输出注明 upsert 和 delta_count，避免累计重复计数。
- 板载摄像头须使用对应旋转坐标系的独立 zones JSON。未标定的示例区域仅允许显式 DEBUG 模式运行，屏幕和事件均标记 DEBUG，业务确认计数保持为 0；只有人工确认的配置才能产生正式 confirmed 事件。默认示例区域不能作为实际柜口几何验收。
- 实时部署在 `/userdata/flow_demo/models/` 按模型 SHA-256 缓存，传输和复用时校验内容，运行目录以符号链接引用，避免多轮测试占满 `/tmp`；保留既有运行证据。会话异常退出或未处理帧时不能标记判定完整。

## 数据与标注

- 检测训练集以安全帽摆拍照片为主，辅以真实柜体视频抽帧；检测标注为单类别 YOLO 框。当前收到的 `dataset/PPE.zip` 是 Roboflow YOLOv8 六类 PPE 数据集，训练准备阶段只保留 `helmet` 并重映射为 class `0`，不能把其余 PPE 类别直接混入当前出入检测器。照片覆盖不同款式、颜色、尺寸、朝向、柜内摆放、柜口穿越、反光和遮挡。
- 动作评测集保留完整视频及人工真值，记录动作方向、数量、时间范围、开关门 PTS 和不确定原因。
- 训练、验证和测试按完整视频或完整会话划分；同一视频的相邻帧不得跨集合。
- 空手伸入、柜内移动、过渡区折返、遮挡、多个安全帽重叠／合并应出现在评测素材中。首版要求过渡区持续处于摄像头可见范围内，不把“关门后过渡区不可见”作为常规场景。负样本应覆盖帽子、球体、碗状物、头部／衣物、包装物等易混淆物；这些只用于降低误报，不作为 `helmet` 正样本。
- 首轮建议先拍约 200–300 张照片和 10–12 段短视频做机位与可见性试拍；数量是采集建议，不是已确认的最低数据规模，也不代表这些试拍视频应全部作为最终测试集。

## 验收目标

以下为暂定目标，不是现有结果：

- 动作级事件精确率不低于 95%。
- 满足可见性约束的真实动作，动作级事件召回率不低于 90%；`uncertain` 不计作成功检测。
- 空手伸入、区域内移动和折返负样本不产生确定出入事件。
- 约束外严重遮挡等案例应避免猜测，并按规则报告不确定。
- 最终验收顺序为 PC 视频回放、RV1126B 文件回放、实时摄像头；明确分别报告各阶段结果。

## 非目标
